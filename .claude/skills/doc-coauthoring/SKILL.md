# 文档协作撰写工作流

本 skill 提供了一个结构化工作流，用于引导用户进行协作式文档创建。担当主动引导者的角色，带领用户经历三个阶段：上下文收集、优化与结构化、读者测试。

## 何时提供此工作流

**触发条件：**
- 用户提到编写文档："写个文档"、"起草一个提案"、"创建一个规格"、"写一份总结"
- 用户提到特定文档类型："PRD"、"设计文档"、"决策文档"、"RFC"
- 用户似乎在开始一项大量的写作任务

**初始提议：**
向用户提供一个结构化的文档协作撰写工作流。说明三个阶段：

1. **上下文收集**：用户提供所有相关上下文，同时 Claude 提出澄清问题
2. **优化与结构化**：通过头脑风暴和编辑，逐节迭代构建内容
3. **读者测试**：用一个全新的 Claude（无上下文）测试文档，在他人阅读前发现盲点

说明这种方法有助于确保文档在他人阅读时效果良好（包括当他们将文档粘贴到 Claude 中时）。询问用户是否想尝试此工作流，还是更倾向于自由写作。

如果用户拒绝，则按自由模式工作。如果用户接受，进入阶段一。

## 阶段一：上下文收集

**目标：** 缩小用户所知与 Claude 所知之间的差距，为后续的智能引导打好基础。

### 初始问题

首先询问用户关于文档的元信息：

1. 这是什么类型的文档？（例如：技术规格、决策文档、提案）
2. 主要受众是谁？
3. 希望读者阅读后产生什么影响？
4. 是否有模板或特定格式需要遵循？
5. 还有其他需要了解的约束或上下文吗？

告知用户可以用简略方式回答，或以任何方便的方式提供信息。

**如果用户提供了模板或提到了文档类型：**
- 询问是否有模板文档可以分享
- 如果提供了共享文档的链接，使用相应的集成工具获取
- 如果提供了文件，直接读取

**如果用户提到编辑现有的共享文档：**
- 使用相应的集成工具读取当前状态
- 检查是否有图片缺少 alt-text
- 如果存在没有 alt-text 的图片，说明当其他人使用 Claude 理解该文档时，Claude 将无法看到这些图片。询问是否需要生成 alt-text。如果需要，请用户将每张图片粘贴到对话中以生成描述性 alt-text。

### 信息倾倒

初始问题回答完毕后，鼓励用户倾倒所有已有的上下文。请求以下信息：
- 项目/问题的背景
- 相关的团队讨论或共享文档
- 为什么不采用替代方案
- 组织上下文（团队动态、历史事件、政治因素）
- 时间压力或约束
- 技术架构或依赖关系
- 利益相关者的关切

告知用户不必担心组织方式——先全部倒出来。提供多种提供上下文的方式：
- 意识流式的信息倾倒
- 指向团队频道或讨论串
- 链接到共享文档

**如果集成工具可用**（例如 Slack、Teams、Google Drive、SharePoint 或其他 MCP server），提示可以使用这些工具直接拉取上下文。

**如果未检测到集成工具且在 Claude.ai 或 Claude 应用中：** 建议用户可以在 Claude 设置中启用 connector，以便直接从消息应用和文档存储中拉取上下文。

告知用户在初始倾倒完成后会提出澄清问题。

**上下文收集过程中：**

- 如果用户提到团队频道或共享文档：
  - 如果集成工具可用：告知将立即读取内容，然后使用相应的集成工具
  - 如果集成工具不可用：说明无法访问。建议在 Claude 设置中启用 connector，或直接粘贴相关内容。

- 如果用户提到未知的实体/项目：
  - 询问是否应搜索已连接的工具以了解更多信息
  - 等待用户确认后再搜索

- 随着用户提供上下文，跟踪已了解的内容和仍不清楚的部分

**提出澄清问题：**

当用户表示初始倾倒已完成（或在提供了大量上下文之后），提出澄清问题以确保理解：

根据上下文中的空白生成 5-10 个编号问题。

告知用户可以用简略方式回答（例如"1: 是的，2: 看 #频道，3: 不行因为要向后兼容"），链接到更多文档，指向频道供阅读，或继续信息倾倒。以最高效的方式进行即可。

**退出条件：**
当问题体现出充分理解时——能够询问边界情况和权衡取舍，而不需要解释基础知识——说明上下文收集已足够。

**过渡：**
询问用户在此阶段是否还有更多上下文要提供，或者是否可以开始起草文档。

如果用户想补充更多，继续收集。准备好后，进入阶段二。

## 阶段二：优化与结构化

**目标：** 通过头脑风暴、筛选和迭代优化，逐节构建文档。

**向用户说明：**
解释将逐节构建文档。每个章节的流程：
1. 提出关于应包含内容的澄清问题
2. 头脑风暴 5-20 个选项
3. 用户指示保留/删除/合并哪些
4. 起草该章节
5. 通过精确编辑进行优化

从不确定性最多的章节开始（通常是核心决策/提案），然后处理其余章节。

**章节排序：**

如果文档结构已明确：
询问用户想从哪个章节开始。

建议从不确定性最多的章节开始。对于决策文档，通常是核心提案。对于规格文档，通常是技术方案。摘要类章节最好放到最后写。

如果用户不确定需要哪些章节：
根据文档类型和模板，建议 3-5 个适合该文档类型的章节。

询问这个结构是否合适，或者是否需要调整。

**结构确定后：**

为所有章节创建带占位符文本的初始文档结构。

**如果可以使用 artifact：**
使用 `create_file` 创建 artifact。这为 Claude 和用户提供了一个可共同工作的框架。

告知用户将创建包含所有章节占位符的初始结构。

创建包含所有章节标题和简短占位符文本（如"[待撰写]"或"[内容待填]"）的 artifact。

提供框架链接并指示可以开始填充每个章节。

**如果无法使用 artifact：**
在工作目录中创建一个 markdown 文件。命名应适当（例如 `decision-doc.md`、`technical-spec.md`）。

告知用户将创建包含所有章节占位符的初始结构。

创建包含所有章节标题和占位符文本的文件。

确认文件已创建并指示可以开始填充每个章节。

**对于每个章节：**

### 步骤一：澄清问题

宣布将开始处理 [章节名称] 章节。提出 5-10 个关于应包含内容的澄清问题：

根据上下文和章节目的生成 5-10 个具体问题。

告知用户可以用简略方式回答，或直接说明需要涵盖的重点。

### 步骤二：头脑风暴

为 [章节名称] 章节，根据章节复杂度头脑风暴 [5-20] 个可能包含的内容。关注：
- 之前分享的可能被遗忘的上下文
- 尚未提及的角度或考量

根据章节复杂度生成 5-20 个编号选项。最后，如果用户需要更多选项，可以继续头脑风暴。

### 步骤三：筛选

询问用户哪些要保留、删除或合并。请求简短理由以帮助了解优先级，为后续章节提供参考。

提供示例：
- "保留 1,4,7,9"
- "删除 3（与 1 重复）"
- "删除 6（受众已了解此内容）"
- "合并 11 和 12"

**如果用户给出自由形式的反馈**（例如"看起来不错"或"大部分可以但是..."）而非编号选择，提取其偏好并继续。解析用户想保留/删除/修改的内容并应用。

### 步骤四：缺口检查

根据用户选择的内容，询问 [章节名称] 章节是否还有遗漏的重要内容。

### 步骤五：起草

使用 `str_replace` 将该章节的占位符文本替换为实际起草的内容。

宣布将根据用户选择的内容起草 [章节名称] 章节。

**如果使用 artifact：**
起草完成后，提供 artifact 链接。

请用户通读并指出需要修改的地方。说明具体的反馈有助于了解用户风格，为后续章节提供参考。

**如果使用文件（无 artifact）：**
起草完成后，确认完成。

告知用户 [章节名称] 章节已起草在 [文件名] 中。请用户通读并指出需要修改的地方。说明具体的反馈有助于了解用户风格，为后续章节提供参考。

**给用户的关键说明（在起草第一个章节时包含）：**
提供说明：不要直接编辑文档，而是告诉需要修改什么。这有助于了解用户的写作风格，为后续章节提供参考。例如："删除 X 条目——已被 Y 涵盖"或"让第三段更简洁"。

### 步骤六：迭代优化

当用户提供反馈时：
- 使用 `str_replace` 进行编辑（永远不要重新打印整个文档）
- **如果使用 artifact：** 每次编辑后提供 artifact 链接
- **如果使用文件：** 确认编辑已完成即可
- 如果用户直接编辑了文档并要求阅读：记录用户所做的修改，并在后续章节中参考（这体现了用户的偏好）

**持续迭代**直到用户对该章节满意。

### 质量检查

连续 3 次迭代没有实质性修改后，询问是否有内容可以在不丢失重要信息的前提下删除。

当章节完成时，确认 [章节名称] 已完成。询问是否准备进入下一个章节。

**对所有章节重复以上步骤。**

### 接近完成

当接近完成（80% 以上章节已完成）时，宣布将重新阅读整个文档并检查：
- 章节间的流畅性和一致性
- 冗余或矛盾之处
- 任何"水分"或通用性填充内容
- 每一句话是否都有分量

阅读整个文档并提供反馈。

**当所有章节均已起草并优化完成：**
宣布所有章节已起草完毕。表示将再次审阅完整文档。

审阅整体连贯性、流畅性、完整性。

提供最终建议。

询问用户是否准备进入读者测试，或还需要优化某些部分。

## 阶段三：读者测试

**目标：** 用一个全新的 Claude（无上下文泄漏）测试文档，验证其对读者的效果。

**向用户说明：**
解释现在将进行测试，看看文档对读者是否真正有效。这能发现盲点——那些对作者来说显而易见但可能让他人困惑的内容。

### 测试方法

**如果可以使用 sub-agent（例如在 Claude Code 中）：**

无需用户参与，直接执行测试。

### 步骤一：预测读者问题

宣布将预测读者在试图了解此文档时可能会提出的问题。

生成 5-10 个读者可能实际会问的问题。

### 步骤二：使用 Sub-Agent 测试

宣布将使用全新的 Claude 实例（不携带本次对话的上下文）测试这些问题。

对于每个问题，仅向 sub-agent 提供文档内容和该问题。

总结读者 Claude 对每个问题的正确/错误回答。

### 步骤三：运行额外检查

宣布将执行额外检查。

调用 sub-agent 检查歧义、错误假设、矛盾之处。

总结发现的问题。

### 步骤四：报告与修复

如果发现问题：
报告读者 Claude 在特定问题上遇到了困难。

列出具体问题。

表示将修复这些不足。

对有问题的章节回到优化阶段。

---

**如果无法使用 sub-agent（例如 claude.ai 网页界面）：**

用户需要手动执行测试。

### 步骤一：预测读者问题

询问用户人们在试图了解此文档时可能会提出什么问题。他们会在 Claude.ai 中输入什么？

生成 5-10 个读者可能实际会问的问题。

### 步骤二：设置测试

提供测试说明：
1. 打开一个新的 Claude 对话：https://claude.ai
2. 粘贴或分享文档内容（如果使用支持 connector 的共享文档平台，提供链接）
3. 向读者 Claude 提出生成的问题

对于每个问题，指示读者 Claude 提供：
- 答案
- 是否有歧义或不清楚的地方
- 文档假设读者已具备哪些知识/上下文

检查读者 Claude 是否给出了正确答案或存在误解。

### 步骤三：额外检查

同时请读者 Claude 回答：
- "这篇文档中有什么可能对读者来说是模糊或不清楚的？"
- "这篇文档假设读者已经具备哪些知识或上下文？"
- "是否存在内部矛盾或不一致之处？"

### 步骤四：根据结果迭代

询问读者 Claude 答错了什么或在哪些方面遇到了困难。表示将修复这些不足。

对有问题的章节回到优化阶段。

---

### 退出条件（两种方法均适用）

当读者 Claude 持续正确回答问题且未发现新的不足或歧义时，文档即已就绪。

## 最终审阅

当读者测试通过时：
宣布文档已通过读者 Claude 测试。在结束之前：

1. 建议用户自己做一次最终通读——他们是文档的所有者，对质量负责
2. 建议仔细检查所有事实、链接或技术细节
3. 请用户验证文档是否达到了预期的影响

询问用户是否需要再审阅一次，或者工作是否已完成。

**如果用户需要最终审阅，提供审阅。否则：**
宣布文档已完成。提供几条最终建议：
- 考虑在附录中链接此对话，以便读者了解文档的开发过程
- 使用附录提供深度内容，避免主文档过于臃肿
- 根据真实读者的反馈持续更新文档

## 有效引导的技巧

**语气：**
- 直接、程序化
- 当影响用户行为时简要说明理由
- 不要试图"推销"方法——直接执行

**处理偏离：**
- 如果用户想跳过某个阶段：询问是否跳过此阶段转为自由写作
- 如果用户似乎感到沮丧：承认这比预期花了更长时间。建议加快进度的方法
- 始终给予用户调整流程的主动权

**上下文管理：**
- 全程关注，如果提到的内容缺少上下文，主动询问
- 不要让不足积累——发现时立即处理

**Artifact 管理：**
- 使用 `create_file` 起草完整章节
- 使用 `str_replace` 进行所有编辑
- 每次修改后提供 artifact 链接
- 头脑风暴列表不使用 artifact——那只是对话内容

**质量优先于速度：**
- 不要赶进度
- 每次迭代都应带来有意义的改进
- 目标是一份真正对读者有效的文档
